## Reproduce the release run

Tested with Rust/Cargo 1.100.0, p7zip 17.05 and Homebrew LLVM 23.1.1. Run from the repository root. The commands use fresh output directories.

```sh
evidence=$(mktemp -d)
curl -fL -o "$evidence/firewall.7z" https://github.com/nan-mu/libbpf-mcu/releases/download/v0.1.2-rc.1/firewall.7z
cargo run --locked -- firewall "$evidence/firewall.7z" "$evidence/run1"
cargo run --locked -- verify "$evidence/run1"
cargo run --locked -- firewall "$evidence/firewall.7z" "$evidence/run2"
diff -r "$evidence/run1" "$evidence/run2"
7z x -so "$evidence/firewall.7z" objects/firewall_bpf.o > "$evidence/firewall_bpf.o"
shasum -a 256 "$evidence/firewall.7z" "$evidence/firewall_bpf.o" "$evidence/run1/"*.json
llvm-readelf -h -S -s -r "$evidence/firewall_bpf.o" > "$evidence/readelf.txt"
llvm-objdump -dr "$evidence/firewall_bpf.o" > "$evidence/objdump.txt"
python3 .audit/taskbook/mcp/sailspan/firewall/verify-firewall.py "$evidence" "$evidence/run1"
```

LLVM identified `xdp` (section 3, file offset 64, length 184 bytes) and function entry `firewall` (ELF symbol 11 at slot 0). The ordinary Node slot groups were `[0–4]`, `[6]`, `[8]`, `[10,11,12]`, `[15,16]`, `[18–21]`. LDDW at slot 12 occupies both 12 and 13. Conditional Boundary slots 5, 7, 9, and 17 all target slot 22 and have fallthrough at 6, 8, 10, and 18 respectively. Helper slot 14 falls through to 15. Exit slot 22 has no successor. These are slot coordinates. The output instead refers to logical IDs and the target at slot 22 is ID 21.

The ELF relocation at byte 96 matches `R_BPF_64_64`, symbol 12 `blacklist` in section 5 and an implicit addend of zero. LLVM also shows CO-RE byte-offset relocations at bytes 8, 16, 48 and 80 with BTF type/access pairs `13/0:1`, `13/0:0`, `16/0:2`, and `22/0:9:0:0`. The checked output retains all five relocations on their original instructions. The [independent comparison script](firewall/verify-firewall.py) reads LLVM's section, symbol, machine byte, instruction and relocation output to check the committed sample and reconstruct the Node and Boundary lists.

The relevant encodings are specified by the [Linux BPF ISA](https://docs.kernel.org/bpf/standardization/instruction-set.html) and [LLVM BPF relocation documentation](https://docs.kernel.org/bpf/llvm_reloc.html).

The reviewer raised two call-specific questions outside the pinned firewall
instruction set. LLVM 23.1.1 independently assembled `callx r3` to
`8d 03 00 00 00 00 00 00` for bpfel. The first fixture run returned
`callx r0`. The fix in `f05c47cbff4b47e04f15c5ce5a612fe3723dc54d`
reads the low register nibble and keeps the dynamic target diagnostic.
The fixture now checks both the operand and Boundary behavior.

The proposed double-counting of the local-call symbol value was checked
against [libbpf's call relocation](https://github.com/libbpf/libbpf/blob/master/src/libbpf.c#L6721-L6735)
and an independently assembled LLVM object. With a function symbol at
byte 8, LLVM emitted `R_BPF_64_32` and the unrelocated immediate was
`-1`. The formula used by libbpf is `symbol_offset / 8 + imm + 1`.
Sailspan's equivalent formula remains unchanged. The expanded synthetic
fixture checks both a nonzero function symbol with a zero addend and
a section symbol with an 8-byte encoded addend. Both resolve to the
same callee slot 1.

The brief branch's own copies of `GLOSSARY.md` and `decisions.md` were
imported verbatim as support files. The separate main snapshot pinned in
the brief supplied D005 and D006 and the canonical terminology for design
and review. The reviewer used that pinned snapshot. The difference is
accounted for by their distinct source commits.

The primary agent reran formatting, all six integration tests, Clippy,
the two CLI entry points, and the LLVM comparison after the call fix.
The final code snapshot produced bit-for-bit identical firewall output
on both the working tree and a fresh source tree. PR publication and
head verification follow after the branch is pushed.
